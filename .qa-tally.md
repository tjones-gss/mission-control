#### Found
- **BUG #1 (critical, fixed)**: SSE stream `/api/stream` was buffered by the
  global `compression` middleware. With default `Accept-Encoding: gzip`,
  EventSource never fired `onopen`, the header was permanently stuck on
  "disconnected", and live updates never flowed. Repro: `curl -v /api/stream`
  returns 0 bytes until the stream fills a gzip block; `curl -H "Accept-Encoding: identity"`

  `server/middleware/performance.js`.
- **BUG #2 (minor, fixed)**: `useSSE` cleanup called `setConnected(false)`
  unconditionally, which under React StrictMode could race with the remounted
  EventSource's `onopen` and leave the header stuck on "disconnected" even
  when the new connection was healthy. **Fix**: drop the setState from
  cleanup in `client/src/hooks/useSSE.js`.
- **BUG #3 (minor, fixed)**: `npm run dev` in `server/` did not watch
  `./middleware` or `./lib`, so edits to rate limit, compression, CORS,
  config etc. silently required a manual restart. **Fix**: add both dirs
  to `--watch-path` in `server/package.json`.
- **Nit**: `GET /favicon.ico` → 404 on every load (logged as console error).
  Not fixed this run — needs a tiny favicon asset and/or route stub.

### Run #5 — 2026-04-07 (QA loop)

#### Tested

#### Found
- **BUG #6 (real, fixed)**: `GET /api/sessions` returned **500** at
  least once during normal usage. Root cause: `getAllSessions()` in
  `server/parsers/sessions.js` had no try/catch around its
  `fs.readdirSync` calls, so a transient ENOENT/EBUSY (chokidar can
  rename or delete files mid-scan, especially when an active session
  is being written to) would bubble all the way up and the route
  handler also had no try/catch. **Fix**: wrap each readdir in
  try/catch and degrade to a partial list, plus wrap the route in
  try/next(err) so any future surprise becomes a clean 500 with the
  shared errorHandler middleware instead of an unhandled rejection.
- **BUG #7 (real, fixed)**: React `validateDOMNesting` warning —
  `<button>` cannot appear as a descendant of `<button>`. ToolUseBlock
  in `ConversationView.jsx` rendered its header as a `<button>`, and
  inside it embedded `<FilePath>` which itself renders a `<button>`
  (copy-path) and `<a>` (vscode://). Triggered every time you opened
  Detail view on a session containing tool calls with file paths.
  **Fix**: convert ToolUseBlock's outer header from `<button>` to
  `<div role="button" tabIndex={0}>` with `onKeyDown` for Enter/Space
  so keyboard activation still works. No DOM nesting violation,
  same UX, same a11y semantics.
- **Observation (NOT fixed)**: `GET /api/sessions/<id>/messages?limit=N`
  ignores the `limit` query param. The endpoint always returns the
  full message history (~526KB for the test session). Not a bug per
  se, but it's wasteful for large sessions and may bite mobile.
  Refactor target, not a drive-by fix.
- **Observation (NOT fixed)**: Routes `/api/sessions/:id/messages`,
  `/api/sessions/:id/memory`, `/api/sessions/:id/intelligence`,
  `/api/sessions/:id/tool-approval` are declared in
  `server/routes/sessions.js` as `':sessionId/...'` (no leading slash).
  Express normalizes this at runtime so it works, but it's confusing
  and inconsistent with the other routes. Cosmetic.

#### Validated
- Post-fix: 5×curl `/api/sessions` → 5×200 (no flakey 500)

  the console at **0 errors** (was 1 DOM-nesting warning before)

### Run #8 — 2026-04-07 (QA loop)

#### Tested
- POST /api/tasks (no sessionId) — confirmed it 404s as expected
- POST /api/sessions/<id>/message with malformed JSON `{not json`
- GET /api/nonexistent (any unmatched API path)

- Verified the test task file landed at

#### Found
- **BUG #10 (real, fixed)**: All three async route handlers in
  `server/routes/tasks.js` (POST, PUT, DELETE) had `} catch (err) { throw err }`
  blocks. Express 4 does NOT auto-catch async rejections, so any fs
  failure (EACCES, EBUSY, ENOSPC, etc.) became a process-level
  unhandled rejection — the client request hung until the 30s
  request timeout, and no error response was ever sent. **Fix**:
  added `next` parameter and replaced `throw err` with `next(err)`
  in all three handlers so the shared errorHandler middleware can
  serialize a clean 500 JSON response.
- **BUG #11 (real, fixed)**: POST /api/tasks/<sid> accepted an empty
  subject and silently created a task with no title, impossible to
  identify in the board UI. **Fix**: added `subject: 'subject is
  required'` 400 validation matching the rest of the API's style.
- **BUG #12 (real, fixed)**: Any unmatched /api/* request returned
  Express's built-in HTML "Cannot POST X" page instead of a JSON
  error. Forced API consumers to handle two error formats. **Fix**:
  added a JSON 404 catch-all middleware mounted at /api in
  `server/index.js` before the errorHandler. Returns
  `{error, code: 'NOT_FOUND', method, path}`.
- **BUG #13 (real, fixed)**: Body-parser JSON parse errors leaked
  internal parser details to the client (e.g., "Expected property
  name or '}' in JSON at position 1 (line 1 column 2)"). The
  errorHandler returned `err.message` verbatim for any 4xx. **Fix**:
  detect `err.type === 'entity.parse.failed'` in errorHandler and
  return a clean `'Invalid JSON in request body'` with code
  `INVALID_JSON`.
