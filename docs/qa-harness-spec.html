01 — CONCEPT

QA as an embedded field agent

Every product has mental models: the story each user tells themselves about how to use it. The QA harness turns those mental models into runnable scripts — Sonnet adopts a persona, navigates the live UI with Chrome, and reports back where the story breaks.

Traditional QA

  • Spec'd happy-path tests
  • Unit / integration coverage
  • Playwright / Cypress scripts
  • Human QA passes on feature complete
  • Finds regressions, misses UX gaps
→

Sonnet QA Harness

  • Persona-driven: "I am a new user"
  • Browses the live UI like a real human
  • No scripts — Sonnet improvises the path
  • Runs on every PR automatically
  • Finds confusion, missing affordances, UX gaps

The key insight: Playwright tests that your button works. Sonnet QA tests that your button makes sense to a human who just installed the thing.

Go deeper: why LLM-as-user beats scripted automation for UX testing

Scripted automation (Playwright, Cypress) verifies what you built. It does exactly what you tell it and confirms the button is clickable, the form submits, the 200 returns. It cannot tell you whether a first-time user would know to click the button, whether the empty state is paralyzing, or whether the approval modal makes any sense without prior context.

An LLM operating as a persona does something qualitatively different: it interprets the UI the way a human would. When it can't find the next step, that's signal. When it tries three wrong things before finding the right one, that's a friction report. When it navigates successfully but its "inner monologue" expresses confusion, that confusion is a finding.

For Mission Control v0.6 specifically, where the core UX is novel (AI agent oversight, real-time approval flows), scripted tests verify the mechanics. Sonnet personas verify the mental model — which is what will determine whether real users adopt it.

02 — ARCHITECTURE

The QA loop

A CLI script loads a persona, hands it to a Sonnet session with Chrome MCP access, lets it navigate the live app, and collects a structured report. The whole loop takes 5–12 minutes per persona.

  • Stop condition: success path complete, or all flows attempted

03 — PERSONAS

Four failure modes that cover the full user space

Each persona is a specific mental model, not a demographic. They differ in context, speed, and what they'll try next when the obvious path fails.

🆕

New User — "Alex"

"I installed this 10 minutes ago from a blog post. I have no idea what a tool approval is."

BLOCKER RISK: HIGH

Core Success Path — "it worked" looks like:

  1. npx @mission-control/app succeeds, browser opens
  2. Auth token step completed — they knew what to enter
  3. Dashboard loads; empty state makes sense
  4. They find out how to connect a Claude Code agent
  5. First agent appears in the dashboard
  6. An approval request comes in; they understand what it wants
  7. They approve or reject with confidence — not anxiety

Top Failure Modes

  • Auth token: what kind? where?
    Token input has no label explaining what it is, its format, or how to generate one. No npx mc token hint. First real install blocker.
  • Empty dashboard paralysis
    Post-auth, the dashboard is empty. There's no "now do this in your terminal" step. New user stares at a blank screen with no next action.
  • Port 3001 silent failure
    If the backend fails to start (port conflict, Node version), the UI loads but shows no data and no error. Looks working, is broken.
  • No SSE connection indicator
    No visible status showing whether the real-time stream is connected. New user can't tell if they're waiting for events or waiting for a broken connection.
  • Approval modal: cold start anxiety
    First approval request appears with a technical tool call. No explanation of "this is asking permission to run a bash command." Approve or reject with no consequence stated.

UI Flows Exercised

  • / → auth gate → token entry → submit
  • /dashboard → empty state → "connect agent" discovery
  • Backend health check (implicit — does anything load?)
  • SSE stream: does it connect, is it visible?
  • First approval modal → approve → confirmation
  • First approval modal → reject → agent behavior

Questions the UI should answer — but likely doesn't

  • Where do I generate a Mission Control token? Is it my Anthropic API key?
  • The dashboard is empty — is this normal or is something broken?
  • How does my Claude Code project "talk to" Mission Control?
  • What does approving this do? What does rejecting it do?
  • Is the real-time connection working right now?
⚡

Daily Driver — "Sam"

"MC is open in my second monitor. I glance at it every few minutes. I need it to stay out of my way."

FRICTION RISK: HIGH

Core Success Path

  1. Return to MC after closing the tab (session restores)
  2. Dashboard shows 2-3 active agents at a glance
  3. Pending approvals visible without scrolling
  4. Triage queue: approve low-risk ops fast, inspect the risky ones
  5. Jump to specific agent's history when something looks off
  6. Back to coding within 90 seconds of opening the tab

Top Failure Modes

  • Approval queue buildup with no batch ops
    Away for 30 minutes: 12 approvals pending. No "approve all safe" or batch select. Must click through each one individually. This is a triage nightmare that will cause abandonment.
  • Session restore: queue and agents still there?
    Close tab, reopen. Does auth persist? Do pending approvals survive? Does the agent list repopulate? If state isn't restored, daily drivers get a jarring empty start every morning.
  • Opaque approval queue: must click in to see what
    The pending approval row doesn't show the operation type (bash, file_read, etc.) inline. Daily driver has to open each item to triage it. Kills the "glance and decide" workflow.
  • No visual risk differentiation
    A bash:ls and a bash:rm -rf ./dist look identical in the queue. No color, no icon, no risk label. Daily driver treats all approvals with equal attention they can't afford.
  • No agent search or filter
    Running 4 agents. One is doing something weird. Can't type to filter the list. Must scroll and visually scan. At 8+ agents, this is untenable.

UI Flows Exercised

  • Session restore: close tab → reopen → state check
  • Dashboard scan: 3 agents, 5 pending approvals
  • Queue triage: approve/reject × 5, timing measured
  • Agent-specific log view: click into one agent's history
  • Search/filter: try typing agent name in any search box
  • Return to dashboard: how fast is the path back?

Questions the UI should answer — but likely doesn't

  • Which of these approvals is actually risky vs. routine?
  • Can I approve all the file-read operations at once?
  • Where's the agent I was working with on the auth service?
  • What did my agent do while I was in the standup?
  • How do I set it so ls-type commands never need approval?
🔬

Power User — "Jordan"

"I've used MC for six months. I'm going to find the race condition before your users do."

EDGE CASE RISK: HIGH

Core Success Path

  1. Fleet view opens with all 6 active agents visible
  2. Keyboard navigation: Tab/arrows work through the queue
  3. Double-approval attempt handled gracefully (no silent duplicate)
  4. SSE disconnect → reconnect: stream recovers, no missed events
  5. Expired approval: UI shows it as stale, button disabled
  6. Rapid approve × 5 without UI glitch or missed confirmation

Top Failure Modes

  • Race condition: double-approve in two tabs
    Two browser tabs open on same MC instance. Both show the same pending approval. User clicks in both within 200ms. Does the backend handle the duplicate? Does the UI reflect stale state? Most likely: silent inconsistency.
  • SSE stream doesn't auto-reconnect
    Toggle wifi off for 8 seconds, back on. Does the SSE stream recover, or does the dashboard silently stale? No reconnection indicator. Agent events during the gap may be lost.
  • Expired approval not grayed out
    Agent times out waiting for approval, moves on. The approval request stays in the UI as if still actionable. User approves a stale request. Backend error is probably swallowed. No UI feedback.
  • Fleet view degrades past 6 agents
    Fleet view renders 8+ agents. Layout breaks, cards overflow, no pagination or virtualization. At 12+ agents it's a scroll wall.
  • Keyboard shortcuts: undiscoverable or nonexistent
    Power users expect keyboard-driven approval flows. No visible shortcut hints (like ⌘K or ?), no keyboard navigation through the queue. Mouse-only workflow at v0.6 is a power-user dealbreaker.

UI Flows Exercised

  • Fleet view: load with 6+ mock agents
  • Keyboard nav: Tab through approval queue
  • Two-tab double-approval race test
  • SSE: disconnect Chrome network → reconnect → state check
  • Expired approval: wait for timeout → try to approve
  • Rapid-fire: approve 5 items as fast as possible
  • Press "?" or look for keyboard shortcut discovery UI

Questions the UI should answer — but likely doesn't

  • What keyboard shortcuts can I use here?
  • Why does this approval show as "pending" if the agent already moved on?
  • Is my real-time connection live right now? When did it last receive an event?
  • Can I see a raw event log for debugging purposes?
  • Can I set approval rules so I don't have to approve read-only ops?
👥

Co-op Teams — "Alex + 3 contributors"

"We're sharing one MC instance. The team lead runs agents; contributors need visibility and sometimes approve."

CONFLICT RISK: HIGH

Core Success Path

  1. Alex shares the LAN URL (192.168.x.x:5173) with contributors
  2. Contributors open it, auth succeeds (with same token?)
  3. Everyone sees the same agent states in real time
  4. One contributor approves a request; all others see it update
  5. No one approves the same request twice (conflict is prevented)
  6. Team lead can see who did what (basic attribution)

Top Failure Modes

  • Concurrent approval conflict: both click at once
    Alex and Jamie both see the same pending approval. Both click Approve within 300ms of each other. The backend likely handles first-write-wins, but does the loser's UI update? Does it say "already approved by another user"? Almost certainly not — it probably silently fails or shows a stale state.
  • LAN setup is completely undocumented in UI
    No "Share access" button. No instructions for CORS config. Contributor opening the LAN URL gets an auth wall with no guidance. The team lead has no way to invite contributors from within the UI.
  • Single-token auth model breaks team use
    MC uses one shared auth token. All contributors use the same token. There's no user identity, no roles, no way to see "who is currently using this." Feels like sharing a root password.
  • No attribution: who approved what?
    The approval history shows what was approved and when, but not who approved it. Team leads need this for accountability. Audit trail missing entirely.
  • State sync latency on slow LAN
    Each client has its own SSE connection. When one person approves, how quickly do other clients update? If there's a 2-3 second lag, two people can see the same request as "pending" at the same time and both try to act.

UI Flows Exercised

  • LAN URL entry from a second machine (or 2nd browser profile)
  • Auth: two browser sessions with same token
  • Concurrent approval: both sessions click within 500ms
  • State sync: approve in session A, check latency in session B
  • Attribution: check approval history for "who did this"
  • Any "Share access" or "Team" UI discovery

Questions the UI should answer — but likely doesn't

  • How do I share this with my team securely without giving everyone the same token?
  • Who approved that last operation 20 minutes ago?
  • Can I see who else is currently looking at this dashboard?
  • How do I prevent a contributor from approving destructive operations?
  • If two of us are watching, who should approve?

Adversarial note: Each Sonnet persona run should be instructed to try at least one thing that "shouldn't" work — a wrong token format, a rapid double-click on approve, opening a second tab. The most revealing bugs in v0.6 live at the intersection of "normal user behavior" and "edge case the dev didn't think to test."

What Sonnet actually does

Sonnet uses Chrome MCP to navigate, read the page DOM, click elements, and fill inputs — exactly like a browser automation test, except the "test" is a language model interpreting the page the way a human would. It reports confusion in prose, not just pass/fail.

For ambiguous UI states ("I see a spinner, I'll wait 5 seconds") it applies human-like patience rather than timing out immediately.

05 — OUTPUT SCHEMA

Structured enough to diff, human enough to act on

Every run produces a JSON report with machine-parseable pass/fail and prose observations. The HTML viewer surfaces findings by severity so the team can triage in 2 minutes.

Go deeper: CI integration and report diffing

The JSON report is designed to be diffable between runs. A CI step can compare confusion_points[].id against the previous run's report to detect new findings. If a severity: "blocker" appears that wasn't in the baseline, the PR check fails.

Recommended CI behavior: run New User + Daily Driver on every PR. Fail the check if any new blocker or high severity confusion point is introduced. Emit the HTML report as a CI artifact for human review.

The regression_risk field is set by Sonnet based on its assessment of whether the changes it observed could break flows that were previously working — a heuristic judgment, not a precise measurement, but useful for prioritizing review.

07 — IMPLEMENTATION

Minimal viable harness using tools you already have

The MVP is a Node script, four markdown files, and a GitHub Actions workflow. No new infrastructure, no dedicated QA server. Sonnet and Chrome MCP do the work.

File structure

qa/
  runner.js          # CLI entry point
  personas/
    new-user.md      # Sonnet system prompt
    daily-driver.md
    power-user.md
    co-op-teams.md
  schemas/
    report.json      # JSON Schema for output
  reports/           # gitignored, CI artifact
  viewer/
    index.html       # report HTML renderer
  run-all.sh         # all 4 personas

Persona prompt anatomy

Each .md persona file is the full Sonnet system prompt for that run. It contains:

  • Identity: Who you are, your technical background, your mental model of the app
  • Success path: The ordered list of tasks to attempt
  • Adversarial instructions: "Try this edge case. If you find a confusing moment, note it verbatim."
  • Output format: The JSON schema the report must conform to
  • Scoring rubric: What counts as blocker vs. friction vs. cosmetic

08 — GAPS

Five personas the four above won't catch

The defined personas cover the planned usage space. These gaps cover failure modes outside the happy path — situations where real users break things the core four personas wouldn't reach.

The Frustrated Returner

Used MC 6 weeks ago, hasn't touched it since. Returns after a version bump. Tests whether UI changes are discoverable, whether muscle memory still works, and whether any "what's new" guidance exists.

Catches: silent deprecations, moved UI elements, missing changelogs, broken saved state from old versions

The Setup Debugger

Follows the new user path but hits a real error: wrong Node version, port 3001 in use, missing env var, corporate firewall blocking SSE. Tests whether error messages are actionable and recovery paths exist.

Catches: cryptic error messages, missing diagnostic tools, no "common issues" page, error states that look like success states

The Passive Observer

Doesn't want to approve or reject — just wants to watch what agents are doing for oversight and audit purposes. Tests whether MC has value in read-only mode and whether the event stream is readable without acting on it.

Catches: missing read-only access model, audit log gaps, no way to follow an agent without being in the approval loop

The Interrupted User

Opens MC with 3 active agents, gets pulled into a 45-minute meeting, returns to the tab. Tests session expiry, queue persistence, SSE reconnection, and whether the "pick up where I left off" path works.

Catches: session expiry without warning, lost queued approvals, stale agent status indicators, zombie SSE connections

The Security Skeptic

Evaluates MC for team use and scrutinizes: what data is logged, what the auth model actually enforces, whether the API responds without auth, what's in the network tab. Tests trust-building and security posture.

Catches: unauthenticated endpoints, data retention surprises, missing security documentation, misleading auth UI

Sprint 3 recommendation: Prioritize the Setup Debugger — it will be the most common first-run experience for new users who encounter any friction. It catches a class of bugs (error states) that the New User persona won't reach because Sonnet will typically be able to resolve issues that a real confused user might bounce on.

09 — SPRINT 2 SPEC

What ships, who owns it, what "done" means

Eight deliverables. P1 is the working harness; P2 is CI integration; P3 is full persona coverage. Ship P1 in Week 1 to get the first real findings before the sprint ends.

Priority Deliverable Description Acceptance Criteria
P1 qa/runner.js CLI script: --persona + --url → JSON report via Sonnet + Chrome MCP Runs headlessly, exits with valid JSON matching the report schema, handles Chrome MCP errors gracefully
P1 Persona: New User qa/personas/new-user.md — complete system prompt covering cold-start auth, empty state, first agent, first approval Sonnet successfully navigates the success path on a clean MC install AND finds the 3 documented failure modes on v0.6
P1 Persona: Daily Driver qa/personas/daily-driver.md — return visit, queue triage, session restore Sonnet attempts all 6 flows; correctly identifies the queue buildup and opaque approval row as friction points
P1 Report JSON Schema Formal JSON Schema for the output report; runner validates output before saving Schema covers all fields; invalid reports rejected with a useful error message
P2 HTML Report Viewer Single-file HTML renderer for report.json — shows pass/fail/friction by severity Opens from file system, renders all finding types, sortable by severity
P2 GitHub Actions workflow Per-PR CI run: New User + Daily Driver; fails on new blocker/high-severity findings vs. baseline Runs in <20 min; attaches HTML report as artifact; does not fail on pre-existing findings
P3 Persona: Power User qa/personas/power-user.md — Fleet view, keyboard shortcuts, edge cases, race conditions Sonnet attempts double-approval race, SSE disconnect, expired approval, rapid-fire queue
P3 Persona: Co-op Teams qa/personas/co-op-teams.md — two-session setup, concurrent approvals, attribution Runner supports --sessions 2 flag; concurrent approval conflict scenario documented in report

Definition of "done" for the harness

  • Runs without human intervention from npm run qa:new-user
  • Produces a valid JSON report every time (even on Sonnet error)
  • Finds at least 3 of the 5 documented v0.6 failure modes per persona
  • Does not require changes to the MC app itself to run
  • Report is readable by a developer who wasn't in the room

Out of scope for Sprint 2

  • Mobile / responsive persona runs
  • Missing personas (Returner, Setup Debugger, etc.)
  • Auto-remediation suggestions beyond prose notes
  • Performance benchmarking (load times, SSE latency)
  • Accessibility testing (separate Playwright audit)

The first run will be humbling. Schedule 30 minutes with the team after the first New User persona run against v0.6. The findings will be real, specific, and actionable — and there will be more of them than expected. That's the point. Better from Sonnet at 9am than from a real new user at 9pm.
